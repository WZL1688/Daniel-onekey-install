# 双交易所现货套利与库存平衡工具

Node.js 20.18+，本机 Web 管理界面，默认端口 **8888**。支持 Binance Global HMAC 现货 API 与 OKX Global 现货 API 的适配代码，不含三角套利、转账或提现功能。采用原生前端、精确十进制计算、本地加密凭据和持久化安全状态。

**当前交付边界：本地功能已实现并通过测试，但实盘验收尚未完成。当前云环境阻止访问交易所，且未能读取 OKX 官方文档，因此 OKX 实盘有后端锁定。不能将本版本视为已验证可投入真金白银的成品。** 不要为了开启实盘自行修改 `docs/verification.json`；它是开发验证记录，不是用户设置。

## 本地运行

使用 Linux、macOS 或 Windows WSL2。当前实测为 Debian 13 / Node.js 24；原生 Windows 未验证（目录 fsync、权限与进程锁依赖 POSIX 行为）。

```bash
cd spot-arbitrage
npm ci
npm test
npm start
```

浏览器访问本机 `127.0.0.1:8888`。服务只绑定回环地址并校验 Host、Origin、会话和 CSRF；不要直接暴露到公网，也不支持通过普通域名反向代理绕过校验。界面每两秒读取本机缓存，不触发交易所请求。项目没有构建步骤或外部前端 CDN。

可用环境变量：`PORT`（默认 8888）、`ARB_DATA_DIR`（默认项目下 `data`）。代理沿用 `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`，使用系统和 Node 配置的 CA 验证。不得关闭证书验证。Node 使用非标准信任库时，配置 `NODE_EXTRA_CA_CERTS` 指向受信 CA 文件。

## 已实现功能

- 实时机会、动态平衡、账户余额、Key 状态、提交记录、API 调度、错误与设置八个页面。
- 公平轮转关注交易对，每轮一个；根据用户额度控制最小间隔，保留最后有效盘口及过期标记。
- 公共请求不带私人 Key；查询 Key 轮换且验证同一 UID；交易 Key 只下单／撤单。
- 分交易所统一优先级队列、在途盘口合并、预留最终复核额度、固定窗口与额外滚动窗口保护、响应头限额合并、持久化退避。
- 实际穿透盘口，合并重复价格并排序；拒绝空、交叉、错误交易对和畸形数据。共同步长按两所步长的最小公倍数计算。
- 数量向下取整后重新计算深度均价、限价和利润。买限价向上、卖限价向下按 tick 取整；分别扣两侧手续费与固定缓冲，不增加固定比例滑点。
- 默认金额失败后尝试备用金额；同时要求深度净利润及限价保守利润达标。
- 所有提交经过统一最终复核：更新规则、两所余额、当前交易对开放订单、价格过滤上下文，再刷新完整返回范围的盘口。前端不可传入数量和价格。
- 买卖代币数量完全相同，IOC 限价委托；第一腿 API 返回并持久化后才发送第二腿。没有自动查询已提交订单的成交状态，没有自动补单或重发。
- 订单号、账户 UID 无损解析，避免 JavaScript 大整数精度丢失。意图在请求发出前落盘；进程中断后的在途意图恢复为未知并保留阻塞。
- 每资产独立配置动态平衡、单笔金额、停止差额和最大亏损。平衡与普通套利门槛分离，最大亏损默认 0，设正数必须额外确认，不得超过金额。
- 最近 10 天记录可分页读取；实际亏损显示红色。未核对批次不伪造已实现收益。

## 配置顺序

1. 先确保交易所和官方文档可以访问，完成剩余接入验证。区域实体不同的 Binance/OKX 不能直接套用 Global 接口。
2. 在“API Key 状态”添加查询专用 Key。OKX 需要 Passphrase。点击验证，以交易所返回 UID 验证账户；不同 UID 会隔离，不进入轮换池。
3. 添加交易专用 Key，填写对应已验证账户的 UID，确认归属。代码从不查询此 Key，因此无法同时在远端查询验证其归属与权限。界面明确区分“用户声明归属”和“查询已验证”。请在交易所限制权限、关闭提现、启用 IP 白名单。
4. 设置真实 taker 费率、金额、缓冲、两项利润门槛和关注交易对。预留双边足够库存及手续费资产。
5. 等待有效规则、盘口与余额。每笔正式提交还会重新刷新，不使用界面上的旧值直接授权。
6. 只有接入文档检查与账户验证全部通过后，才能输入“确认开启实盘并理解双腿风险”开启实盘。动态平衡还需逐资产开启。

所有真实账户 Key 都应在本机界面输入，**不要发送到聊天或写进代码、脚本、日志**。

## 必须理解的交易边界

两所下单不具备原子性。IOC 可能完全不成交、部分成交，或第一腿成功第二腿失败。相同的提交数量不代表相同的实际成交数量。手续费也可能从基础币、报价币或折扣币扣除，利润仅为按配置费率折算的估计。

因此本工具的“仅提交模式”选择保守行为：**任何已受理、未知或双腿不完整的批次都会阻止所有新批次，直到人工在交易所核对并处理残余敞口**。它不是无人值守无限连续成交机器人。“归档”只隐藏到归档状态，不会抹掉风险阻塞；重启也不会解除。

“人工核对”要求先停止实盘，在交易所按订单号／Client ID 核对每一腿，确认没有开放余量，填写实际成交量、净收益、核对依据及库存处理。此流程是你的人工声明，程序不会将声明伪称为交易所返回的成交证据。核对后旧余额会失效，必须刷新余额后才能重新开启。

不要在同一账户／IP 上同时运行未纳入本工具额度管理的机器人。Binance 会合并观测到的 IP 用量，但无法控制其他程序在观测后的请求；OKX 的共享 REST/WS 用户限额也不能被 Key 轮换扩大。建议独立子账户和预留充足限额。

“完整盘口”指每次 REST 返回的完整有效快照，而非交易所无限深度：Binance 请求前 100 档，OKX 前 400 档，界面显示返回与合并后的档位总数和前五档；超过已获取深度的订单会拒绝，不假定额外流动性。

## 限速规则

优先级 0：最终复核与下单；1：实时盘口；2：平衡（复用实时数据，提交后提升至 0）；3：余额／查询验证；4：手动扫描；5：自动扫描。全市场扫描在实盘开启时暂停。

Binance 同时使用 `exchangeInfo.rateLimits` 的所有 REQUEST_WEIGHT、RAW_REQUESTS、ORDERS 窗口、IP 使用量响应头和额外保守配置上限（100–1200 权重/分钟，默认 600），并保留 50 权重给复核。OKX 使用保守的聚合公共 8/2 秒、私人 4/2 秒、接口桶及总量 100–240/分钟（默认 120），比常见官方接口限额更严格；OKX 正式规则仍待官方文档复核。

429／403／418 和 OKX 限流码会退避，尊重秒数或 HTTP 日期形式的 Retry-After；网络故障短暂指数退避。请求不会在失败后自动重试。之后的新轮询仅在退避结束后排队；交易、撤单失败或未知均不会自动重发或切换 Key 重发。

## 持久化与备份

`data/state.json` 保存设置、加密凭据、批次、限速窗口、滚动用量、退避、缓存与安全阻塞；原子替换并 fsync。`data/master.key` 是本机 AES-256-GCM 加密主密钥（0600），目录为 0700，单进程锁防止并发写入。

凭据加密依赖本机主密钥文件与操作系统权限，不能抵御已取得该账户或 root 权限的攻击者。备份时先正常停止服务，将整个 `data` 目录一起备份到安全位置；不能只备份 state.json，也不能把 master.key 发给别人。主密钥丢失时拒绝覆盖生成。数据损坏时拒绝静默重置。

每次重启自动交易强制关闭，其他配置与风险状态恢复。重启不会恢复网络连接或“已经成交”的假设。记录不自动删除；交易记录量很大时应在停止服务后保留完整审计备份再做迁移，不能直接删除未知批次。

## 长期运行

`systemd/spot-arbitrage.service` 提供 Linux 用户服务模板。将项目放在主目录下 `spot-arbitrage`，检查 `ExecStart` 的 Node 路径；NVM 用户应改为绝对 Node 路径。

```bash
mkdir -p ~/.config/systemd/user
cp systemd/spot-arbitrage.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now spot-arbitrage
systemctl --user status spot-arbitrage
journalctl --user -u spot-arbitrage
```

不要与手工启动实例同时运行。默认只在失败后重启，进程重启仍关闭实盘。无 systemd 的云容器使用平台进程管理或 `npm start`；当前云测试实例已启动，但不能保证聊天结束后平台保留进程。
